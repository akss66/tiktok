# Vulcan Private Message Inbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a persistent, multi-account private-message inbox with manual account monitoring, Windows notifications, knowledge-grounded three-level LLM replies, one automatic reply per conversation, and recoverable low-frequency processing.

**Architecture:** Electron owns account BrowserViews, WebSocket lifecycle, Windows notifications, and direct execution in the correct account page. The local Node backend owns SQLite state, inbox APIs, LLM decisions, and a persistent serial work queue. New messages always flow BrowserView -> Electron monitor -> backend ingest -> SQLite -> notification/analysis queue; sends flow persistent queue -> Electron worker -> exact account BrowserView -> backend result.

**Tech Stack:** Electron 43, React 19, Node.js CommonJS, better-sqlite3, Vitest, existing Douyin userscript Bridge, OpenAI-compatible `LLMClient`.

## Global Constraints

- Only accounts explicitly enabled by the user may be monitored; the global “enable after login” default remains off.
- Keep the Douyin WebSocket connected, drain its local message queue every 60 seconds, and stagger multiple accounts.
- Retry monitor connections after 30 seconds, 1 minute, 2 minutes, 5 minutes, and 10 minutes; cap retries at 10-minute intervals.
- Delay automatic replies by a random 60 to 180 seconds.
- Every conversation may send at most one automatic reply until the user explicitly reauthorizes it.
- All DM analysis and send work is persistent and serial; Douyin writes must never run concurrently.
- New installations and upgrades default to `manual`; monitor-on-login defaults to `false`.
- The app does not monitor or notify after the Electron application fully exits.
- Text messages are the only required message type in this iteration.
- Unsupported or unverified history synchronization must surface `realtime_only` or `incomplete`; it must not report a successful history sync.
- Do not implement platform-detection bypass, anti-detection, or fingerprint spoofing.

- [ ] **Step 3: Add the schema and repository**

Add tables `dm_monitor_states`, `dm_conversations`, `dm_messages`, `dm_reply_drafts`, and `dm_work_items`. Use `UNIQUE(account_id, conversation_id)` for conversations and `UNIQUE(account_id, conversation_id, message_key)` for messages. Generate `message_key` as `index:<index>` when an index exists; otherwise hash `sender|conversation|message_type|content|floor(timestamp/30000)` with SHA-256.

```js
function messageKey(message) {
  const index = String(message.index || message.message_index || '').trim();
  if (index) return `index:${index}`;
  const source = [message.sender, message.conversation_id, message.message_type, message.content,
    Math.floor(Number(message.timestamp || Date.now()) / 30000)].join('|');
  return `sha256:${crypto.createHash('sha256').update(source).digest('hex')}`;
}

function ingestMessages(db, input = {}) {
  if (!input.accountId) throw new Error('accountId is required');
  return db.transaction(() => {
    const result = { inserted: 0, duplicates: 0, conversations: [], insertedMessages: [] };
    for (const raw of input.messages || []) {
      const saved = insertMessageIdempotently(db, input.accountId, raw, messageKey(raw));
      if (!saved.inserted) { result.duplicates += 1; continue; }
      result.inserted += 1;
      result.insertedMessages.push(saved.message);
      result.conversations.push(touchConversationForIncomingMessage(db, input.accountId, saved.message));
    }
    return result;
  })();
}
```

- [ ] **Step 3: Implement serial claim and persistent retries**

Use `BEGIN IMMEDIATE` transactions. `claimNextWork` must refuse a second claim while any non-expired item is `running`. `failWork` schedules `next_run_at` with delays `[30000, 60000, 120000, 300000, 600000]` and moves to `failed` after the configured attempt limit.

```js
function claimNextWork(db, workerId, now = Date.now()) {
  return db.transaction(() => {
    recoverInterruptedWork(db, now);
    if (db.prepare("SELECT 1 FROM dm_work_items WHERE status = 'running' LIMIT 1").get()) return null;
    const row = db.prepare(`SELECT * FROM dm_work_items
      WHERE status = 'pending' AND (next_run_at IS NULL OR next_run_at <= ?)
      ORDER BY created_at ASC LIMIT 1`).get(new Date(now).toISOString());
    if (!row) return null;
    db.prepare(`UPDATE dm_work_items SET status='running', worker_id=?, lease_expires_at=?, updated_at=? WHERE id=?`)
      .run(workerId, new Date(now + 60000).toISOString(), new Date(now).toISOString(), row.id);
    return getWork(db, row.id);
  })();
}
```

Wrap each existing Douyin write item execution in `mvp-workflows.js` with lease acquisition/release. A read-only search or comment pull must not acquire the write lease.

async function runSend(work) {
  const lease = await acquireLease(`dm:${work.id}`);
  if (!lease.acquired) return defer(work.id, 30000);

  }
}
