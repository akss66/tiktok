# Vulcan 私信工作台与 AI 回复闭环设计

## 1. 目标

在现有线索私信发送能力之上新增独立的私信工作台，使运营人员可以：

- 仅为手动启用的抖音账号监听新私信。
- 在应用内查看会话与完整消息记录，并进行人工回复。
- 收到新消息时获得 Windows 系统通知，并从通知直达对应会话。
- 使用本地知识库和运营规则生成回复草稿。
- 在设置中选择全部人工、分级自动或完全自动三档回复模式。
- 每个会话最多自动发送一次，之后必须人工处理，除非用户手动重新授权。
- 在页面刷新、网络中断和应用重启后恢复监听，并增量补拉遗漏消息。

本功能继续遵循现有系统的低频原则：所有抖音写操作和 LLM 分析任务均进入持久化串行队列，不并发发送。

## 2. 已有能力与技术边界

原项目用户脚本已经具备以下私信基础能力：

- 创建私信会话。
- 发送文本私信。
- 建立私信 WebSocket 连接。
- 解码新消息通知并写入页面内存队列。
- 从页面内存队列读取新消息。

当前缺口：

- 没有持久化会话和消息历史。
- 没有桌面端持续监听服务。
- 没有完整实现离线历史消息增量补拉。
- 没有 Windows 通知、未读状态和通知跳转。
- 没有面向会话的 LLM 草稿与审核流程。

因此，现有 `pollDMs()` 只能作为读取页面内存队列的通道，不能视为离线历史同步。离线补拉必须单独实现并真实验证私信历史协议；无法完整补拉时，系统必须明确显示同步不完整，不能静默假定没有新消息。

## 3. 总体架构

新增四个边界清晰的模块：

1. **私信监听服务**
   - 按账号管理监听开关、WebSocket 状态、同步游标和退避重连。
   - 仅处理已登录且启用了监听的账号。
   - 负责从账号 BrowserView 的 Bridge 读取新消息和补拉历史消息。

2. **私信存储服务**
   - 对会话、消息、草稿和监听状态进行 SQLite 持久化。
   - 以账号、会话 ID 和消息序号实现幂等去重。
   - 先保存消息，再触发通知、LLM 分析和回复任务。

3. **私信决策服务**
   - 结合最近会话、线索来源、启用的知识库和根目录运营规则生成结构化判断。
   - 决定生成草稿、转人工或允许一次自动发送。
   - 不直接调用抖音发送接口。

4. **私信发送服务**
   - 使用现有私信发送能力和持久化串行队列。
   - 在执行前再次校验登录状态、回复模式、自动回复额度和是否已有人工回复。
   - 自动发送采用 60 至 180 秒随机延迟。

模块之间通过结构化服务接口通信，不继续把监听、存储、决策和发送逻辑堆入 `mvp-workflows.js`。

## 4. 监听与恢复规则

### 4.1 启用方式

- 设置页提供“账号登录后自动开启私信监听”，默认关闭。
- 账号页提供每个账号独立的私信监听开关。
- 新账号继承全局默认值。
- 用户手动修改账号开关后，该账号使用显式设置，不再被全局默认覆盖。
- 系统稳定检测到登录状态后等待约 30 秒，再启动监听，避免登录过程中重复连接。
- 应用完全退出时停止所有监听；下次启动按保存设置恢复。

### 4.2 在线监听

- WebSocket 长连接由抖音推送新消息。
- 桌面应用每 60 秒读取一次页面内存消息队列；该操作不重复请求抖音消息接口。
- 多账号检查时间错开，避免同一时刻集中执行。
- 浏览器面板可以隐藏或最小化，但启用监听的账号 BrowserView 会话必须保持存活。

### 4.3 断线与离线恢复

- WebSocket 断开后按 30 秒、1 分钟、2 分钟、5 分钟、10 分钟退避重连，最高保持 10 分钟间隔。
- 页面刷新、跳转或 Bridge 重注入后恢复 WebSocket 和消息读取循环。
- 应用重启后恢复监听设置、同步游标、未完成草稿和待发送任务。
- 离线消息按每个账号、每个会话的最后同步位置增量补拉。
- 消息补拉必须分页、串行执行，并持久化进度。
- 登录失效时停止该账号监听并标记“需要重新登录”，不得持续刷新登录接口。
- 补拉失败时保留最后成功游标并显示“消息同步不完整”，下次从该位置继续。

## 5. 数据模型

### 5.1 `dm_monitor_states`

- `account_id`
- `enabled`
- `setting_source`：继承全局或账号显式设置
- `connection_status`
- `last_queue_poll_at`
- `last_sync_cursor`
- `last_sync_at`
- `next_retry_at`
- `last_error`

每个账号唯一一条记录。

### 5.2 `dm_conversations`

- `account_id`
- `conversation_id`
- `conversation_short_id`
- `ticket`
- `lead_id` / `peer_user_id` / `peer_name`
- `status`：未读、待人工、跟进中、已完成、忽略
- `unread_count`
- `last_message_at`
- `last_message_preview`
- `auto_reply_consumed`
- `auto_reply_authorized_at`
- `reply_mode_override`
- `last_synced_index`

账号与会话 ID 联合唯一。

### 5.3 `dm_messages`

- `account_id`
- `conversation_id`
- `message_index`
- `message_key`：平台消息序号或稳定内容指纹
- `sender_id`
- `direction`：收到或发出
- `message_type`
- `content`
- `sent_at`
- `status`：已收到、待发送、发送中、已发送、失败、取消
- `raw_json`

账号、会话 ID 和 `message_key` 联合唯一。平台提供稳定消息序号时直接生成 `message_key`；否则使用发送方、会话、内容、消息类型和时间窗口生成稳定内容指纹。该键必须持久化，不能只在页面内存中去重。

### 5.4 `dm_reply_drafts`

- `account_id`
- `conversation_id`
- `source_message_id`
- `intent`
- `lead_level`
- `knowledge_entry_ids`
- `confidence`
- `reason`
- `content`
- `decision`：仅草稿、允许自动、强制人工、忽略
- `review_status`
- `send_task_id`

现有 `dm_leads` 保留评论获客来源，并通过 `lead_id` 与会话关联，不重复建立客户记录。

## 6. 私信工作台 UI

采用已确认的 A 方案：三栏运营台。

### 6.1 左栏：会话列表

- 账号筛选和账号监听状态。
- 全部、未读、待人工、跟进中筛选。
- 搜索客户昵称或消息内容。
- 展示客户、最后消息、时间、未读数和意向标记。

### 6.2 中栏：会话内容

- 按时间显示完整消息记录和发送状态。
- 展示线索来源评论与视频入口。
- 支持手动输入、采用 AI 草稿、失败重试。
- 明确显示“本会话已自动回复一次，后续转人工”。
- 用户手动回复后，取消该会话所有尚未发送的自动回复任务。

### 6.3 右栏：客户与 AI

- 客户意向、来源视频、来源评论和跟进状态。
- 命中的知识库条目及 LLM 判断理由。
- AI 回复草稿、重新生成、编辑、采用并发送。
- 显示当前回复模式和自动回复额度。
- 提供“重新允许自动回复”操作；执行后只恢复一次额度。

### 6.4 响应式规则

- 宽屏保持三栏同时可见。
- 中等宽度下缩窄会话列表，保证聊天内容优先。
- 宽度不足时将右栏收进抽屉，不压缩聊天区到不可用宽度。
- 不使用横向滚动承载核心操作。

## 7. LLM 决策规则

### 7.1 输入上下文

- 当前收到的消息。
- 最近 20 条会话记录。
- 客户来源评论和来源视频信息。
- 启用的本地知识库条目。
- 根目录运营规则和回复风格文档。

### 7.2 结构化输出

- 意图分类。
- 意向等级。
- 命中的知识条目 ID。
- 置信度。
- 建议回复。
- 是否允许自动发送。
- 判断理由。

输出解析失败、缺少关键字段或引用无效知识条目时一律转人工。

### 7.3 三档回复模式

1. **全部人工**
   - 所有消息只生成草稿。
   - 新安装和版本升级后默认使用该模式。

2. **分级自动**
   - 知识库明确命中。
   - 置信度达到设置阈值，默认 85%。
   - 不属于强制人工类别。
   - 当前会话尚未使用自动回复额度。
   - 满足全部条件后才允许延迟并自动发送一次。

3. **完全自动**
   - 普通互动不要求明确知识库命中也可生成一次自动回复。
   - 仍受强制人工类别和每会话一次额度限制。

投诉、退款、冲突、知识不足、报价不明确、敏感内容和 LLM 结果不稳定时，无论模式如何均强制转人工。

### 7.4 自动回复额度

- 每个会话最多自动发送一次。
- 自动任务创建与 `auto_reply_consumed` 更新必须在同一数据库事务内完成。
- 重复事件、重复分析和应用重启不得重复消耗或重复发送。
- 用户手动点击“重新允许自动回复”后，该会话恢复一次额度，并记录授权时间。

## 8. 设置与通知

设置页新增“私信与通知”分区：

- 回复模式。
- 知识库命中置信度，默认 85%。
- 自动发送延迟，默认随机 60 至 180 秒。
- 登录后默认开启监听，默认关闭。
- Windows 通知开关。
- 通知是否显示消息摘要。
- 免打扰时段。

账号页允许覆盖监听开关和回复模式。

Windows 通知规则：

- 新消息成功写入数据库后才发送通知。
- 同一条消息只通知一次。
- 通知包含账号、客户昵称和可配置的消息摘要。
- 点击通知打开主窗口并定位到对应账号和会话。
- 应用最小化时可以通知；应用完全退出后不监听、不通知。
- 应用内同步显示未读数量和账号级未读标记。

## 9. 队列与并发规则

- LLM 分析任务使用持久化串行队列。
- 私信发送任务使用持久化串行队列。
- 抖音写操作全局并发数固定为 1。
- 多账号发送仍共用全局写队列，不按账号并发。
- 自动发送前随机等待 60 至 180 秒。
- 请求失败使用退避重试，不立即连续重发。
- 应用重启后恢复未完成任务；发送前重新检查会话最新状态。

## 10. 错误处理

- Bridge 未连接：保持消息和任务状态，提示打开或恢复对应账号浏览器，不盲目发送。
- 登录失效：停止监听和发送，标记需要登录。
- LLM 不可用：保留收到的消息并转人工，不影响手动回复。
- 知识库为空：分级自动模式不得自动发送。
- 自动任务等待期间出现人工回复：取消自动任务。
- 自动任务等待期间设置改变：按最新设置重新判定。
- 发送结果不确定：不得直接重发，先标记待确认，避免重复私信。
- 通知失败：不影响消息持久化和未读状态。

## 11. 分阶段实施与验收门

### 阶段一：可靠收信与人工回复

- 会话和消息持久化。
- 手动账号监听。
- WebSocket 新消息接收。
- 三栏私信工作台。
- Windows 通知和通知跳转。
- 人工回复串行发送。

阶段一实测通过后再开启 AI 自动流程。

### 阶段二：知识库与三档回复

- 结构化 LLM 判断。
- 草稿生成和知识引用。
- 三档模式及账号覆盖。
- 每会话一次自动回复额度。
- 延迟发送、人工接管和重新授权。

### 阶段三：离线增量补拉

- 私信历史协议实现。
- 会话级同步游标。
- 分页串行补拉。
- 断网、重启和页面刷新恢复。

## 12. 测试计划

### 单元测试

- 消息去重与后备指纹。
- 会话未读数和最后消息更新。
- 自动回复额度事务锁定。
- 三档模式决策矩阵。
- 敏感内容强制转人工。
- 人工回复取消待发送自动任务。
- 退避时间计算和同步游标更新。

### 集成测试

- Mock Bridge 推送新消息并持久化。
- WebSocket 重复事件不会产生重复消息或通知。
- LLM 返回固定知识命中时生成草稿或单次自动任务。
- 应用重启恢复监听状态与队列。
- 多账号消息、会话和浏览器状态完全隔离。
- 点击通知定位到正确会话。

### 手动验收

1. 登录账号并手动开启监听。
2. 隐藏浏览器后从另一个账号发送私信。
3. Vulcan 显示新会话并弹出 Windows 通知。
4. 点击通知进入正确会话。
5. 分级自动模式命中知识库后延迟自动回复一次。
6. 再发送一条消息，系统只生成草稿并通知。
7. 手动重新授权后，才允许再次自动回复一次。
8. 刷新抖音页面、短时断网并重启应用，验证不丢失、不重复。
9. 同时监听多个账号，确认发送仍严格串行。
10. 关闭账号监听，确认不再建立私信连接或拉取消息。

## 13. 本轮不做

- 应用完全退出后的系统服务或托盘常驻监听。
- 无人工授权的无限连续 AI 对话。
- 多条私信并发发送。
- 绕过平台限制、伪装检测或规避风控。
- 语音、图片、视频等复杂消息的自动理解和自动回复；首版只保证文本消息闭环。
